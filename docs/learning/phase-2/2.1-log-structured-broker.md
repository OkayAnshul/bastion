# 2.1 Why a log-structured broker

**Phase:** 2 · **Date:** 2026-09-14 · **Time spent:** written during the build

> **About the numbers.** Broker throughput and latency are **unmeasured** so far; Phase 3 benchmarks
> the serving path. Configuration values come from `configs/streaming.yaml`.

## What problem does this solve?

A payment passes through many systems that care about it at different speeds. The scoring path
needs features now. The feature builder has to update Redis. The offline store has to keep every
event for training. Monitoring has to watch distributions. If the payment gateway called each of them
directly, one slow consumer would slow payments, a crashed consumer would lose events, and nobody
could replay yesterday.

A log-structured broker puts one durable, ordered log between producers and consumers. Everyone reads
at their own pace, and anyone can re-read from any point.

## How it works

- **Append-only log, split into partitions.** A topic is a set of partitions. Each is an ordered,
  immutable sequence of messages identified by *offsets*. Messages are retained by time or size,
  not deleted when read.
- **Keys choose partitions.** Bastion publishes `transactions.raw` and `transactions.labels` keyed by
  `card_id` (6 partitions each). Every event for one card lands on the same partition, in order.
  That per-card ordering is the only ordering Bastion relies on.
- **Consumer groups share the work.** Consumers with the same `group.id`
  (`bastion-feature-builder`) split the partitions between them. A second builder instance takes
  half the partitions without any coordination code.
- **Offsets are the consumer's bookmark.** The feature builder commits offsets only *after* the
  Redis writes succeed, so a crash replays the last few messages rather than losing them:
  **at-least-once** delivery.
- **Idempotency makes at-least-once safe.** The producer uses `enable.idempotence` (broker-side
  deduplication of retries). The builder's writes are idempotent too: sorted-set members are keyed by
  transaction id, and earliest-seen times use `ZADD LT`. Processing a message twice leaves the store
  exactly as processing it once, and a unit test checks that.

```
gateway/simulator ──produce(key=card_id)──► transactions.raw [p0 p1 p2 p3 p4 p5]
                                              │     │
                     feature builder (group) ◄┘     └► raw sink, monitoring (their own groups)
                        writes Redis, then commits offsets
```

## Why we chose it here

- **ADR-001:** Redpanda speaks the Kafka protocol, so the code uses the standard `confluent-kafka`
  client, and it runs as one container that starts in seconds.
- **Replay is a feature, not an accident.** The batch/stream parity test, the drift demo (Phase 6)
  and the latency benchmark all depend on replaying the same events through the same path.
- **Several consumers, one source.** The feature builder now; the raw Parquet sink and monitoring
  later, each at its own pace.

## What we rejected and why

- **Redis Streams.** It would mean one less service, but it has a weaker partitioning and
  consumer-group story at scale, and the Kafka vocabulary is what the industry uses (ADR-001).
- **The gateway writing to Redis directly.** It couples payment latency to feature-store health, and
  there is no replay.
- **Exactly-once transactions.** Kafka transactions add real complexity. Idempotent writes give the
  same end state for this workload.
- **Topic creation in a one-shot container.** Application code creates topics idempotently instead,
  which keeps `docker compose up --wait` simple (ARCHITECTURE.md §7).

## Where it breaks

- **Ordering is per partition only.** A device or merchant shared by cards on different partitions
  sees its events interleaved by processing time. Bastion's store tolerates that: histories are sorted
  by event time, and earliest-seen maps keep the minimum.
- **Hot keys.** One card (or, with IEEE-CIS proxies, one hub-like card key) sending far more events
  than others overloads one partition.
- **Rebalancing pauses consumption** while partitions move between consumers, so lag spikes when
  instances start or stop.
- **Retention bounds replay.** An event older than the retention period can no longer be replayed from
  the broker; the offline store has to hold history.

## The interview answer

"Payments go onto a Redpanda log keyed by card id, so each card's events stay ordered on one partition.
Consumers read at their own pace: the feature builder updates Redis and only then commits its
offsets, which gives at-least-once delivery. I made every Redis write idempotent, so a replayed
message changes nothing. Being able to replay the same log is what makes my parity test and drift demo
possible."
