# 2.2 Event time vs processing time

**Phase:** 2 · **Date:** 2026-09-14 · **Time spent:** written during the build

> **About the numbers.** The replay-duration example is illustrative arithmetic. Parity results come
> from the unit tests described in 2.4.

## What problem does this solve?

Every event has two clocks. **Event time** is when the payment actually happened (`event_ts`), or
when its chargeback arrived (`label_ts`). **Processing time** is when some consumer got around to it.
They differ by network delay, consumer lag, a backlog after an outage, and deliberately so during
replay.

A feature like "transactions on this card in the last hour" must mean the hour before the *payment*,
not the hour before the consumer ran. Otherwise the same payment gets different features depending on
how busy the system was, and the stream stops matching the batch data the model was trained on.

## How it works

Bastion anchors everything that affects a feature value to event time:

- **Windows.** A read for a transaction at time *q* covers `[q - w, q)` in event time
  (`bastion.features.definitions`).
- **Storage.** Redis histories are sorted sets *scored by event time*. An event inserted late still
  lands in its correct place, and a read covers exactly the right range.
- **Reads are as-of.** Upper bounds are exclusive (`(q` in `ZRANGEBYSCORE`), so an event already
  ingested with a *later* timestamp is invisible to the read. Processing progress cannot leak the
  future.
- **Labels have their own event time.** A chargeback counts once `label_ts < q`, however early or late
  the label message was consumed. Merchant rates use labels known by the start of the transaction's
  day.
- **Trimming uses event time** as well: events older than the longest window before the newest event
  are dropped.
- **Replay paces by event time.** `speedup=3600` plays one event-hour per wall-second. *Illustrative:*
  a 183-day dataset would take 183 × 24 × 3600 / 3600 = 4,392 s, about 73 minutes. The feature values
  are the same at any speed.

Only one thing uses processing time, deliberately: **key TTLs**. They are a wall-clock memory
safety net for entities that go quiet, not the mechanism that defines windows.

```
event time:       09:00:00  09:00:30  09:01:10
processing time:  09:00:02  09:01:15  09:01:12     (the second event arrived late)
read at q=09:01:10 covers [09:00:10, 09:01:10) in EVENT time → finds 09:00:30 once it is ingested
```

## Why we chose it here

- **ADR-004:** batch and stream must compute identical values. Batch has no processing time at all;
  it only knows event timestamps. The stream can match it only by computing in event time too.
- The drift demo (Phase 6) replays months of events quickly. Processing-time windows would compress
  a day's velocity into seconds and invent card-testing bursts.

## What we rejected and why

- **Processing-time windows** (in-memory counters reset on a wall-clock timer). Simpler, and they
  break parity and replay.
- **Waiting for a watermark before answering.** Stream processors like Flink hold results until they
  are "sure" no earlier event will arrive. A payment decision cannot wait, so Bastion answers
  immediately from what has been ingested, and accepts that a very late event may be missed.
- **Pre-aggregated counters updated on ingest.** They are cheap to read but go stale: a stored
  "count in the last hour" is wrong a minute later unless something decrements it. Reading raw
  history as of *q* avoids that.

## Where it breaks

- **Late events are missed, not wrong.** If a card's earlier payment is still in the queue when a later
  payment is scored, the later one's velocity undercounts. That is inherent to deciding in real time.
- **Producer clock skew.** Event time is only as good as the clock that stamped it. A gateway with a
  fast clock creates "future" events.
- **Timezones and day boundaries.** Merchant rates refresh at UTC midnight. For IEEE-CIS even the
  time anchor is arbitrary (ADR-011).
- **Fast replay vs TTL.** At high speedups event time outruns the wall clock, so TTLs almost never fire
  during a replay. Trimming does the real work, which is intended, but it means TTL behaviour is only
  realistic in real time.

## The interview answer

"Every feature is defined in event time: the hour before the payment, not before the consumer ran.
Redis stores histories as sorted sets scored by event timestamp and reads with an exclusive upper
bound, so late inserts land in the right place and later events can't leak into earlier reads. That
makes a replay at 3,600 times real speed produce exactly the features batch training saw. The one
trade-off I accept is that decisions don't wait for stragglers: a very late event can be missed, but
never counted in the wrong window."
