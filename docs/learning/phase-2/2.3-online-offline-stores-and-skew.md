# 2.3 Online and offline stores, and train/serve skew

**Phase:** 2 · **Date:** 2026-09-14 · **Time spent:** written during the build

> **About the numbers.** The skew measurement comes from the synthetic leakage experiment (log 1.2).
> Batch timing comes from the synthetic table in Phase 1. Serving latency is **unmeasured** until
> Phase 3.

## What problem does this solve?

A model is trained on features computed offline, over months of history in Parquet, in minutes. It is
served with features computed online, for one transaction, in milliseconds, from a fast store. If the
two computations disagree even slightly (a window boundary, a null rule, a rounding step), the model
receives inputs it was never trained on. Nothing crashes. Scores quietly get worse, and nobody notices
until the fraud losses do. That is **train/serve skew**.

## How it works

**Two stores, one set of definitions (ADR-004):**

| | Offline | Online |
|---|---|---|
| Stores | the canonical event table (Parquet) | Redis sorted sets and maps |
| Computes | features for every row at once | features for one transaction |
| Executor | `bastion.features.batch` | `bastion.features.online` |
| Definitions | `bastion.features.definitions` | the *same* functions |
| Speed | 277,608 synthetic events in 0.98 s (measured) | one pipelined round trip per read (latency unmeasured) |

The online executor fetches one transaction's context: the card's last 30 days, the device's last 7,
earliest-seen times and label counts. It builds small arrays and calls exactly the functions the
batch executor calls on the whole table. Nothing about what a feature *means* is written twice.

**Exact, not approximate.** Money is summed in integer milli-units, and second moments in integer
cents. Both executors therefore feed identical integers into the one float step at the end, and parity
can be tested with *equality* rather than a tolerance (see 2.4).

**What skew does to a model (measured on synthetic data).** The leakage experiment includes a model
trained on features computed one way and scored on features computed another way, which is skew in its
purest form. The leaky model scored PR-AUC **1.0000** on its own features and **0.6465** on
production-style features. The model was unchanged; only the feature computation differed.

**A tripwire at load time.** Each model bundle records a fingerprint of its feature spec (inputs, order,
categorical vocabularies). A bundle whose spec file doesn't match the fingerprint refuses to load.
Phase 3 extends that check to the features the service can build.

## Why we chose it here

- **ADR-004** names skew "the second silent killer" and forbids separate implementations.
- Bastion's features are history-dependent (windows, first-seen times, label arrivals), which is
  exactly where a hand-written serving copy drifts from the training code.

## What we rejected and why

- **pandas for training, hand-written Python for serving.** It is the classic trap: two
  implementations that agree on the happy path and differ on nulls, ties and boundaries.
- **Precomputed aggregates in Redis** ("count_1h = 3"). They are stale the moment time moves, and
  cannot answer as-of questions, which the parity test needs.
- **Adopting Feast now.** It is the right idea at scale, but it would hide the mechanism this phase
  exists to build (ADR-003). It can be adopted after the hand-rolled version is understood.
- **Logging serving features and training on them only.** Google's Rules of ML recommends it, and it
  guarantees no skew going forward, but there is no history to train on at the start. Bastion will
  log served features in its decision log (Phase 3) as a second line of defence.

## Where it breaks

- **Vendor attributes aren't recomputed.** IEEE-CIS's C, D and V fields arrive in the request payload.
  If an upstream system changes how it computes them, Bastion's parity tests cannot see it.
- **Online memory is finite.** Entities idle past the lifetime TTL are forgotten, so their ages and
  familiarity features differ from a batch recomputation (ARCHITECTURE.md §7).
- **Label lag online.** A label consumed later than its `label_ts` is invisible for a moment online,
  while batch sees it instantly.
- **Someone "optimises" a sum back to floats**, and exact parity quietly becomes approximate. The parity
  tests would catch it; that is what they are for.

## The interview answer

"Training and serving compute features with the same functions: one definitions module, two
executors. Batch runs it over the whole event table; the online path fetches a card's recent history
from Redis in one round trip and calls exactly the same code. Money is summed as integers, so I can
test parity with equality, not a tolerance. I also measured what skew costs: a model trained on
features computed differently from how they're served dropped from a perfect PR-AUC to 0.65 on my
synthetic data, with no code error anywhere."
