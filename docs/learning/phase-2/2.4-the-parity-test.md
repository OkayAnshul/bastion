# 2.4 The parity test

**Phase:** 2 · **Date:** 2026-09-15 · **Time spent:** written during the build

> **About the numbers.** The durations were measured: locally for the in-memory tests, and in GitHub
> Actions run 34849391993 (commit `4bafa89`) for the Redpanda/Redis tests. Both sets use small
> synthetic tables, so they show correctness, not throughput.

## What problem does this solve?

ADR-004 says the stream must compute exactly the features the model was trained on. Saying so is
free. The parity test is what turns the claim into evidence: replay the same events through the
streaming path and check, transaction by transaction, that every feature equals the batch value.
ROADMAP makes it Phase 2's exit criterion ("without it, everything downstream is untrustworthy") and
requires it to run in CI.

## How it works

Parity is checked at three levels, each catching a different kind of bug:

| Level | Test | What it catches |
|---|---|---|
| Function | an "online-style" call on one card's history equals the batch row (`test_features.py`) | the definitions themselves diverging between call patterns |
| Store | online features from an in-memory Redis equal batch features (`test_online_features.py`) | key layout, serialisation, as-of reads, trimming, idempotency |
| System | events replayed through **real Redpanda** into **real Redis** equal batch features (`tests/integration`) | producer/consumer wiring, JSON round trips, partitioning, commit order |

Two replay modes run at the store and system levels:

1. **Bulk, then as-of.** Ingest every transaction and label first, then read each transaction's
   features as of its own time. This works only because every Redis structure can be queried as of
   the past, so it tests exactly that property. Trimming is off, because old history must survive.
2. **Interleaved, production order.** For each transaction: read its features, then publish it; labels
   are published at their arrival time. Through Redpanda, every read first waits until the feature
   builder has processed everything published so far. Trimming is on, so this also proves trimming
   never removes an event a later read needs.

A **hypothesis** property test adds 40 random small event logs (two cards, random devices, merchants,
amounts, fraud flags, 45 days) at the store level.

**Equality, not tolerance.** The comparison is `DataFrame.equals` on the full feature table: same
columns, same dtypes, same nulls, identical floats. That is possible because money is summed in
integer milli-units and second moments in integer cents. Both executors feed identical integers into
the same final float operations.

**Isolation.** Each system test creates its own topics, consumer group and Redis key prefix from a
random run id, so reruns and parallel jobs never read each other's data.

**Measured:**

- In-memory store tests: 8 tests passed in 8.80 s locally, including the 40-example property test.
- CI job `stream-parity` (run 34849391993): both Redpanda/Redis tests **passed in 15.81 s**. The
  whole job, including starting Redpanda and Redis with `docker compose up --wait`, took 56 s.

## Why we chose it here

- **ADR-004** names the test explicitly, and ROADMAP makes it the Phase 2 exit criterion.
- The online store is new code with many ways to be subtly wrong: an inclusive range where it should
  be exclusive, a trimmed event still inside a window, a label counted twice. Only an end-to-end
  comparison catches all of them at once.

## What we rejected and why

- **Spot checks on a few transactions.** Boundary bugs show up on the rare event that lands exactly on a
  window edge or a shared timestamp, which a spot check rarely picks.
- **Comparing within a tolerance.** It would hide a systematic drift (such as an off-by-one-millisecond
  window) as long as the drift stayed small.
- **Bulk mode only.** It never exercises trimming, or the order in which reads and writes actually
  happen in production.
- **Mocking Kafka in the system test.** A mock would pass while the real consumer and producer
  configuration were wrong, and that configuration is part of what is being tested.

## Where it breaks

- **Coverage is only as good as the data.** Synthetic tables and small hypothesis ranges may never
  produce, say, a card with thousands of events or an amount near the int64 overflow guard.
- **One consumer.** The tests don't cover several feature-builder instances, consumer-group rebalancing,
  or a crash between the Redis write and the offset commit.
- **Redis under memory pressure.** The store is configured with `noeviction`, so the tests never see
  eviction. A different eviction policy would silently break parity.
- **CI time bounds size.** The system tests replay a few thousand events, not months of IEEE-CIS traffic.
- **Vendor attributes** pass through the event payload unchanged, so parity says nothing about them.

## The interview answer

"My parity test replays the same events through Redpanda and the streaming feature builder into Redis,
then compares every feature for every transaction with the batch computation, using equality rather
than a tolerance. It runs in two orders: ingest everything and read as of the past, and the production
order of read-then-write with trimming on. It runs in CI against real Redpanda and Redis on every push;
the latest run passed both tests in about 16 seconds. Exact equality is possible because money is summed
as integers, so there's no floating-point slack to hide a real bug."
