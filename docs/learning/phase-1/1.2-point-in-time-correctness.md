# 1.2 Point-in-time correctness: why fraud models look brilliant and then fail

**Phase:** 1 · **Date:** 2026-09-14 · **Time spent:** written during the build

> **About the numbers.** Worked examples come from Bastion's synthetic table (seed 7, 183 days,
> 3,000 cards) and the leakage experiment (`bastion experiment leakage`). The leakage gap on
> IEEE-CIS, which is the number this entry exists for, is **unmeasured** until the dataset is downloaded.

## What problem does this solve?

Picture the feature "how many times has this card been used in the last 24 hours?". In a notebook it
is one line: group by card and day, count. That line quietly counts transactions that happen *after*
the one being scored, and the transaction itself. The model learns from those counts, the offline
score looks brilliant, and in production, where the future does not exist yet, the feature means
something else and the model falls apart.

Point-in-time correctness is the discipline of computing every training feature from **only what
was known strictly before that transaction**: earlier events, and labels that had already arrived.
It is ADR-003, and the most consequential decision in this project.

## How it works

### The four ways a feature pipeline leaks

`bastion.features.naive` implements them on purpose, one per block, so the experiment can measure
them:

| Leak | Naive version | What it smuggles in |
|---|---|---|
| Self + future | count per card inside a *calendar* hour or day | the transaction itself and every later one in the bucket |
| Future | mean and std of the card's amounts over *all* history | spending that has not happened yet |
| Future | "card has used this device before" as "pair appears more than once" | true even on the very first use |
| Target | the card's fraud-label count, or the merchant's fraud rate, over all rows | the row's own label, before its chargeback exists |

### What honest looks like

`bastion.features.definitions` answers one question for every feature: *what was true strictly
before time q?*

- **Windows exclude their end.** A window of length *w* at query time *q* covers `q - w <= ts < q`.
  For card events at 0 s, 30 s, 60 s and 120 s, the 1-minute counts are `[0, 1, 2, 1]`. At 60 s the
  window is [0 s, 60 s) and holds two events. At 120 s it is [60 s, 120 s) and holds one. Two events
  in the same second never see each other; IEEE-CIS has one-second resolution, so this matters.
- **One pass, no loops.** Entity and time are packed into one sortable integer, `(entity << 42) | ts`.
  Two binary searches then find each window's start and end for every row at once, and cumulative
  sums give counts and totals. Money is summed in integer milli-units, so batch and streaming sums
  agree exactly rather than to within a float tolerance.
- **Distinct counts without sets.** Each occurrence of a merchant *covers* the query times at which
  it is that merchant's latest earlier occurrence inside the window. The distinct count is then
  "covers started before q" minus "covers ended before q": two more binary searches. It is checked
  against brute force by a property test.
- **Labels count only once they arrive.** `card_prior_fraud_labels` counts chargebacks with
  `label_ts` before the transaction. The merchant fraud rate uses labels that arrived before the
  start of the transaction's *day*, the way a nightly batch job would. It is shrunk toward the
  global known rate, so a merchant with three known labels is not scored 0% or 100%.
- **A global minimum that is not a leak.** "First time this card used this device" compares the
  pair's earliest timestamp with *q*. Future events cannot pull a minimum below *q*, so including them
  changes nothing. It looks exactly like the naive mistake, and it is correct.

This is an as-of join generalised to windows and label arrival. `merge_asof` with
`allow_exact_matches=False` gives the "strictly before" part for a single lookup.

### How we know it holds

`tests/unit/test_features.py` generates random event logs with hypothesis, picks a cutoff, deletes
every event after it (and those events' labels), and asserts that no feature at or before the cutoff
changes. The honest pipeline passes. `tests/unit/test_naive_features.py` shows the naive pipeline
fails the same idea on a two-transaction example: its first transaction's hourly count is 2 with the
later event present and 1 without it.

### What leakage did to the number (synthetic, measured)

| Variant | Train features | Test features | Test PR-AUC [95% CI] |
|---|---|---|---|
| `naive_temporal` | naive | naive | 1.0000 [1.000, 1.000] |
| `naive_in_production` | naive | point-in-time | **0.6465** [0.599, 0.701] |
| `pit_temporal` | point-in-time | point-in-time | 1.0000 [1.000, 1.000] |

Read the middle row carefully. It is the leaky model scored on features computed the way production
must compute them. Offline it reported 1.0000; against production-style features it scored 0.6465, a
drop of **0.3535 PR-AUC**. That is train/serve skew caused by leakage, and it is the failure mode
that sinks real fraud models.

What the synthetic run *cannot* show is the offline gap between the leaky and honest pipelines: both
score 1.0000. The synthetic attacks are separable by design, so both models sit at the ceiling. That
gap is the IEEE-CIS result this project is waiting on.

## Why we chose it here

- **ADR-003:** training features are point-in-time correct, via as-of semantics on a time-sorted log.
- **ADR-004:** the same definitions will run online (Phase 2). Correctness proven once, in one module,
  carries over to serving, and the batch/stream parity test will check that it does.
- **IEEE-CIS makes leakage unusually tempting.** Labels propagate forward within an account, so
  "has this card had fraud?" computed with future labels is close to reading the answer.

## What we rejected and why

- **Whole-dataset group-bys.** Fast and simple, and they are the leak.
- **Per-card rolling windows in pandas** (`rolling(..., closed="left")`). They handle simple
  counts, but not label arrival, distinct counts or merchant-level rates without a separate code
  path, and a second implementation is exactly what ADR-004 forbids.
- **Adopting Feast first.** Its point-in-time joins are the right tool at scale, but using it before
  building the mechanism by hand would hide the thing this phase exists to understand
  (ARCHITECTURE.md, ADR-003).

## Where it breaks

- **Vendor attributes are opaque.** IEEE-CIS's C, D and V columns are computed by Vesta. Whether all
  of them are point-in-time is undocumented, so the experiment holds them fixed while comparing
  Bastion's own features.
- **Label arrival is simulated.** Real chargeback timing is longer and messier.
- **Day-granular merchant rates** are stale within a day. Fine for a nightly job; it would miss a
  merchant compromised this morning.
- **"Strictly before" discards simultaneous events.** Two genuinely concurrent card-testing probes do
  not see each other. That is the price of determinism.
- **Streaming adds new ways to break it:** late events, clock skew, reprocessing. Phase 2's parity
  test has to cover them.

## The interview answer

"Every feature in my training set is computed from events strictly before that transaction, and from
labels whose chargeback had already arrived. I proved it with a property test: delete everything
after a random cutoff and no earlier feature may change. I also built the leaky version on purpose.
A model trained on leaky features scored a perfect PR-AUC offline, but on features computed the way
production computes them it dropped to 0.65. The first number was measuring the future, not fraud."
