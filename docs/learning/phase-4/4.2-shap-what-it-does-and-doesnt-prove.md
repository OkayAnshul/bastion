# 4.2 SHAP: what it does and doesn't prove

**Phase:** 4 · **Date:** 2026-09-15 · **Time spent:** written during the build

> **About the numbers.** The only measured fact here is a unit test: TreeSHAP contributions plus the
> bias term add up to the model's raw margin, within 1e-5. What reason codes cost in scoring latency
> is **unmeasured** until the Phase 3 benchmark is re-run with the policy engine in place. Whether
> analysts find the codes useful is unmeasured, and nothing in this project can measure it.

## What problem does this solve?

A blocked customer calls support, or an analyst opens a case in the review queue. Both ask the same
question: why? A fraud probability of 0.83 is not an answer. Reason codes are: the handful of inputs
that pushed this transaction's score up the most, in words a person can check against the
transaction ("9 card transactions in the previous hour").

## How it works

**Shapley values.** Treat a prediction as a game in which the inputs are players who share a payout:
how far this prediction is from the model's average output. An input's Shapley value is its average
marginal contribution, taken over every order in which the inputs could "join". It is the only way
to share the payout that satisfies all four of these properties:

- **Efficiency:** the contributions add up exactly to the prediction minus the average.
- **Symmetry:** inputs that contribute equally get equal credit.
- **Dummy:** an input that never changes the output gets zero.
- **Additivity:** for a sum of models, the contributions add.

**TreeSHAP.** Averaging over every order is exponential in the number of inputs. For tree ensembles,
TreeSHAP computes the exact values in polynomial time by walking each tree's paths (Lundberg, Erion
and Lee, 2018). LightGBM ships it as `predict(..., pred_contrib=True)`: one column per input plus a
bias, which together sum to the raw margin (log-odds).

**In Bastion:**

- `ModelBundle.contributions_from_matrix` computes contributions for the exact encoded row that was
  scored. The service keeps that row instead of rebuilding it.
- `top_reasons` keeps the three largest *positive* contributions: the inputs that pushed towards
  fraud. It attaches the value and a readable description for every canonical input.
- Contributions are computed only for reviewed and blocked transactions. Approvals, the large
  majority, pay nothing for explanations. The time is recorded per request as `explain_ms`.
- Calibration is monotonic, so an input that raises the margin also raises the calibrated
  probability. The sign of a contribution means the same thing in both spaces; its size does not.

## Why we chose it here

- ROADMAP Phase 4 asks for reason codes from SHAP top-k, and the case page needs them.
- For tree models TreeSHAP is exact, not an approximation, and LightGBM computes it natively. No
  extra library runs in the scoring path.
- Additivity makes the codes auditable: a test checks that the numbers add up to the margin.

## What we rejected and why

- **LIME.** It fits a local linear model on random perturbations, so two runs can explain the same
  transaction differently. That is a bad property for something shown to an analyst.
- **Global feature importance (gain, permutation).** It says what matters on average, not for this
  payment.
- **The `shap` library in the hot path.** It is a heavy dependency that computes the same TreeSHAP
  values LightGBM already produces.
- **Showing every contribution.** Nobody reads 37 numbers during a review. The top three positive
  ones are the case summary, and the full feature vector is still in the decision record.

## Where it breaks

This section is the reason for the log entry. SHAP values explain **the model**, and only in a
narrow sense.

- **Not causal.** "Card transactions in the previous hour" having the largest contribution means
  the model leaned on it for this row. It does not mean velocity caused the fraud, or that lowering
  it would make the payment legitimate.
- **Correlated inputs share or swap credit.** The 1-hour and 24-hour counts, or spend and count,
  carry overlapping information. TreeSHAP's path-dependent algorithm splits the credit according to
  how the trees happened to split. A retrained model with the same accuracy can tell a different
  story.
- **Relative to a baseline.** Contributions explain the distance from the model's average output
  on its training data. A "positive" input is only unusual relative to that average.
- **Log-odds, not probability.** A contribution of +1.2 does not add 1.2 of anything a customer
  would recognise, and the same log-odds shift moves the probability more near 0.5 than near 0.
- **They explain the score, not the decision.** Bastion's action also depends on the amount, the
  cost assumptions, the review budget and the overrides. A 5,000 USD payment can be blocked at a
  probability where a 20 USD payment is approved. That is why the decision carries its expected cost
  per action, and a case view must show both.
- **Explanations can be gamed.** Slack et al. (2020) built models whose SHAP and LIME explanations
  hide the features they actually use. An explanation is evidence about a model you already trust,
  not a certificate.
- **Anonymised inputs explain nothing.** On IEEE-CIS a top reason like "Vendor attribute C13" is
  honest but useless to a human reviewer.

## The interview answer

"For reviewed and blocked payments the service attaches reason codes: the top three positive TreeSHAP
contributions, which LightGBM computes exactly with pred_contrib, turned into readable statements.
They're additive, and a test checks they sum to the model's margin. But I'm careful about what they
mean. They explain the model's log-odds relative to its average, not causes. Correlated features can
trade credit between retrains, and they explain the score, not the decision, which also depends on
the amount, the costs and the review budget. So the case view shows the expected cost of each action
next to the reasons."
