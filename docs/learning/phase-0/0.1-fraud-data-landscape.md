# 0.1 The fraud data landscape

**Phase:** 0 · **Date:** 2026-09-14 · **Time spent:** written during the build

> **About the numbers.** IEEE-CIS is not downloaded yet, so every IEEE-CIS figure here is
> **unmeasured**. The worked examples use Bastion's synthetic dataset, measured with:
> `bastion data synthetic --days 183 --cards 3000 --seed 7`, then `bastion eda`.
> Synthetic numbers show how the reasoning works; they are not claims about real fraud.

## What problem does this solve?

Before building any model you need to know what fraud data actually looks like. Its shape dictates
nearly every later decision: which metric to report, how to split train and test, which features are
honest, and what the final decision rule optimises. Four facts matter: fraud is **rare**, it is
**unequal** in value, its labels arrive **late**, and in public data the entities are **anonymised**.
Miss any one of them and the project can report excellent numbers that mean nothing.

## How it works

**1. Rare: class imbalance.** In the synthetic dataset, 2,352 of 277,608 transactions are fraud:
**0.85%**. A "model" that approves everything is 99.15% accurate and catches nothing. That is
why accuracy never appears in Bastion's reports. PR-AUC's no-skill value is the positive rate
(0.0085 here), so a PR-AUC is only meaningful next to that base rate.

**2. Unequal: cost asymmetry.** Fraud is 0.85% of transactions but **2.58% of transaction value**.
The distribution is also two-humped:

| Synthetic, USD | Legitimate | Fraud |
|---|---|---|
| Median amount | 32.69 | 3.38 |
| Mean amount | 51.74 | 160.59 |
| p95 amount | 159.21 | 856.91 |

The fraud median sits *below* the legitimate median, while the fraud mean sits *above* it. That split
comes from two attack modes: card-testing probes (a few dollars, to check a stolen card works) and
cash-outs (hundreds to thousands). A count metric scores missing a $3 probe the same as missing a
$2,000 cash-out. A value metric ("fraud value caught") does not. This is ADR-005 in one table.

**3. Late: the chargeback lifecycle.**

```
authorisation      cardholder notices     dispute filed     chargeback      label known
     |------------------------|--------------------|---------------|---------------|
  t = 0 (decision)          days                weeks           weeks        label_ts
```

At decision time `is_fraud` does not exist. It arrives with the chargeback, if at all. Two things
follow:

- **Features** may only use labels whose `label_ts` is before the decision (ADR-003).
- **Training data** must exclude the most recent transactions. Their chargebacks have not landed,
  so they *look* legitimate. Bastion's split leaves a 14-day maturity gap for this (ADR-007).

IEEE-CIS adds a twist, described by the dataset provider (see `docs/data_dictionary.md`): once a card
has a reported chargeback, *later* transactions linked to the same account, email or billing address
are labelled fraud too. Labels propagate forward in time. So "has this card had fraud before?" is a
very strong feature, and a very easy one to leak.

**4. Anonymised: proxy entities.** IEEE-CIS has no card, device, merchant or IP identifiers. Bastion
builds proxies (ADR-011): card from card fields, address and first-seen day; a coarse device
fingerprint; a product/recipient-domain "merchant". Every velocity, entity-risk and graph feature
inherits the weakness of those proxies.

## Why we chose it here

- Imbalance and value asymmetry → value-based headline metrics and a monetary cost model (ADR-005,
  `bastion.evaluation`).
- Delayed labels → temporal splits with a maturity gap (ADR-007, `configs/splits.yaml`) and
  point-in-time features (ADR-003, `bastion.features.definitions`).
- Anonymised entities → one explicit, documented mapping at the dataset boundary (ADR-011,
  `bastion.data.adapter`), so the rest of the system never touches raw IEEE-CIS columns.
- Public *and* synthetic data → IEEE-CIS for credible numbers; synthetic for CI, the stream parity
  test, and attack injection, where the ground truth is known.

## What we rejected and why

- **Accuracy or F1 as the headline.** Accuracy rewards approving everything. F1 weights a $3 miss
  and a $2,000 miss equally, and ignores review capacity.
- **Treating labels as known instantly.** It inflates every offline metric and trains on
  "legitimate" rows that are really unreported fraud.
- **The IEEE-CIS `test_*` files.** They have no labels, so no honest metric can be computed on them.
- **Synthetic data alone.** The author designs the attacks, so a model that catches them proves
  only that the pipeline works.

## Where it breaks

- **Synthetic numbers are easy by construction.** The two fraud modes are cleanly separable in
  amount; real fraud is not that cooperative.
- **IEEE-CIS label propagation** means a fraud rate counts *linked* transactions, not independent
  attacks. A card-level feature can look miraculous for reasons that do not transfer to a system
  with different labelling rules.
- **Time and place.** IEEE-CIS is e-commerce data from about six months, published in 2019. Patterns
  in other markets or payment rails (UPI, for example) differ.
- **Proxies can merge or split customers.** `D1n` is off by one day across midnight boundaries
  because the true reference time is unknown.

## The interview answer

"Fraud data is rare, unequal and late. It's rare, so accuracy is meaningless and I report PR-AUC next
to its base rate. It's unequal: in my synthetic set fraud is under 1% of transactions but more than 2.5%
of the money, with small card-testing probes and large cash-outs, so I measure fraud *value* caught and
monetary loss. It's late: a label exists only when a chargeback arrives weeks afterwards, so every
feature uses only labels available at decision time, and training stops short of the most recent,
immature data."
