# 3.2 Where my 50 ms actually went

**Phase:** 3 · **Date:** 2026-09-15 · **Time spent:** written during the build

> **About the numbers.** Everything here was measured on one laptop (Intel i7-1255U, one service
> worker, Redis in Podman, k6 in a container), using synthetic payloads and history. Profile numbers
> are py-spy samples, which include the profiler's own overhead. The full measurements and their
> caveats are in [`docs/results/phase3/profiling.md`](../../results/phase3/profiling.md).

## What problem does this solve?

ARCHITECTURE §3.3 splits the 50 ms p99 budget by stage: 12 ms for the Redis fetch, 4 ms for
features, 8 ms for the model. ROADMAP Phase 3 asks me to profile, fix the slowest component, and
write down what it was. My guess beforehand would have been the model, or Redis. Both guesses were
wrong, which is the argument for measuring first.

## How it works

I used three instruments, each answering a different question.

1. **Stage timers in the handler** (`perf_counter_ns`, stored with every decision record) show which
   stage's latency grows with load.
2. **A sampling profiler** (py-spy, attached from outside the process) shows where CPU time goes
   *inside* those stages, down to the function and line.
3. **An isolated benchmark** of the suspect function on fixed inputs shows whether a fix helps,
   without HTTP, Redis or load-generator noise. It also compares the two versions' outputs.

**What the first load test showed.** At 400 requests/s, the stage p99s were:

| Stage | Budget (p99) | Measured p99 |
|---|---|---|
| Redis round trip + event-loop wait | 12 ms | 21.28 ms |
| Features + model input row | 4 ms | 2.13 ms |
| LightGBM + calibration | 8 ms | 0.38 ms |

The client-side p99 was 33.16 ms, within budget, but with a long tail. At first sight Redis was the
problem. It wasn't: that stage's median was 0.67 ms, and the stage includes time a request waits for
the single event loop while other requests do CPU work. A slow Redis stage can mean *someone else's*
stage is slow.

**What the profile showed.** Under 200 requests/s:

- 40.5% of all samples were in `features_from_snapshot`.
- 5.4% were in LightGBM prediction.
- Inside feature evaluation, the hottest frames were `_entity_time_key` (5.3%) and NumPy's `_amin`
  (2.8%) and `_amax` (2.5%).

Those frames are input validation and key building, repeated for every time window: once for each
velocity window, each distinct-count window and each device window, per request. The machine-learning
part was the cheapest stage. The expensive part was bookkeeping over many tiny NumPy arrays, where the
per-call overhead of dispatch and checks outweighs the arithmetic itself.

**The fix.** `window_aggregates_many` and `distinct_in_window_many` take a list of windows. They
validate the inputs and build the keys, sort order and cumulative sums once, then do only the
window-dependent step per window.

**What it bought:**

- **Isolated:** feature evaluation fell from 0.458 to 0.279 ms per call (mean, 10,000 calls).
- **Profiled:** feature evaluation fell from 1.944 to 1.380 ms of busy time per request.
- **End to end:** p99 at 400 requests/s fell from 10.4–50.4 ms to 5.7–7.6 ms, over four runs of
  each version.

**Why a small CPU saving removed a large tail.** Queueing. With one event loop, requests take turns
on the CPU. Once the loop is busy most of the time, waiting grows much faster than the work itself.
For illustration only (not a measurement of Bastion): in the simplest queueing model, M/M/1, the
average wait is proportional to ρ/(1 − ρ), where ρ is utilisation. That factor is 9 at ρ = 0.9 and
4 at ρ = 0.8, so taking away a tenth of the load more than halves the waiting. The stage timings are
consistent with this. After the fix, the Redis stage's p99 at 400 requests/s was 2.8–4.1 ms, although
no Redis code changed.

## Why we chose it here

- **Profile before optimising.** The obvious suspects, model inference and Redis, were not where the
  CPU went.
- **Fix inside the shared definition (ADR-004).** The change lives in `features/definitions.py`, and
  both the batch and online paths call it. There is no online-only fast path that could drift from
  training.
- **Prove the fix changed nothing.** A property test checks every window against brute force, the
  existing parity tests still pass, and on 2,000 real snapshots the old and new code return
  byte-identical features.

## What we rejected and why

- **An online-only fast path** (a pure-Python loop over one card's short history). It might be
  faster for tiny histories, but it would be a second implementation of every feature, which is
  exactly what ADR-004 forbids.
- **Dropping the validation.** The checks guard the point-in-time invariants: sorted history, key
  ranges and overflow. They still run, once per call instead of once per window.
- **Numba or Cython.** That adds a compiler toolchain to save fractions of a millisecond. Revisit it
  only if the profile still points at feature evaluation at the load that matters.
- **More worker processes first.** That would hide the per-request cost rather than remove it. It is
  the next lever for throughput, and it needs its own measurement.
- **Caching features between requests.** Every feature is computed as of the transaction's own
  timestamp, so a cached value would be wrong for the next transaction.

## Where it breaks

- **The profiler changes what it measures.** py-spy busy times are inflated relative to unprofiled
  latency. They rank components and compare versions under the same load; they are not latencies.
- **Single profiles are noisy.** Redis pipeline busy time went from 0.818 to 0.992 ms per request
  with no code change.
- **Synthetic history sizes.** A card with thousands of recent events shifts the cost towards sorting,
  and the balance between stages could change.
- **One worker is still the ceiling.** At 800 requests/s neither version keeps up. The first runs
  also failed badly there: redis-py's connection pool ran out, and every extra request became a 500
  with a logged traceback. Those requests now get a 503 with no traceback (see *Overload* on the
  profiling page). Better error handling is not more capacity, though; a second worker is.
- **Sequential A/B runs.** Before and after never ran at the same moment. Reversing the order between
  the first pair and the repeats guards against drift only partly.

## The interview answer

"My scoring endpoint had a 50 ms p99 budget. Per-stage timers under an open-model load test showed a
33 ms p99 at 400 requests per second, and the Redis stage looked guilty. But that stage includes
waiting for the event loop, so I profiled the running service with py-spy. 40% of samples were in
feature evaluation and 5% in LightGBM, and the hottest frames were input validation and key building
repeated for every time window. I changed the shared feature definitions to evaluate all windows in
one pass, and proved the outputs identical with property tests and on 2,000 real snapshots. Feature
evaluation got 39% faster in isolation. The p99 at 400 requests per second went from 10–50 ms to
6–8 ms across four runs each, because near saturation a small cut in CPU time removes a lot of
queueing."

## Open questions

- How much throughput does a second worker process add, and what does 800 requests/s look like then?
- The client-side histogram at 400 requests/s has two peaks, near 1.5 ms and 2.3 ms. Are those two
  kinds of request (for example with and without a device, which skips the device reads), or an
  effect of the client or the event loop? Unexplained so far.
- Would evaluating several waiting requests' features in one NumPy call cut per-request overhead
  further, and what would the batching delay cost at p99?
